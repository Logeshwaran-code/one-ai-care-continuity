# Privacy and compliance (design alignment, not certification)
**DPDP Act 2023 alignment:** purpose-limited data, explicit granular consent (scopes per person, revocable, listed in UI), data minimisation (family dashboard shows booleans/counts), right to access/portability (`/patients/{id}/fhir`), right to erasure (`DELETE /me`; audit rows kept without PHI), security safeguards, breach-response runbook needed (not included). Not yet covered: verifiable parental/guardian consent, children's data, Data Protection Officer processes, consent manager registration, data-localisation review, notice in all languages.
**HIPAA-style practices:** unique user ids, role-based access, audit of every PHI access (including denials), encryption at rest for PHI text fields (Fernet) and in transit (terminate TLS at the proxy), session timeouts (15-min access tokens). Platform is not HIPAA-certified.
**OWASP Top 10:** access control checked server-side per request; parameterised ORM queries; PBKDF2-SHA256 (200k) hashing; JWT algorithm pinned; rate limiting; strict input validation (pydantic); security headers and CSP; no PHI in logs; SW never caches API responses; dependency scanning (`pip-audit`, `bandit`) in CI.
**Interoperability:** FHIR R4 export (LOINC-coded observations). ABDM/ABHA integration is future work.
**Keys:** set `PHI_ENCRYPTION_KEY` and `JWT_SECRET` outside dev (the app refuses to start otherwise). Key rotation procedure is not implemented.
